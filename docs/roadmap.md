### 学習と Zenzai の関係 → **解決済み(決定 0034)**

確定時の `Commit` を配線し、エンジン側で `updateLearningData` を呼ぶようにした
(決定 0024 / 0025)。**辞書変換では学習が効く**ことを実測で確認している —
2位の候補を確定すると次の変換で1位に上がる。

**しかし Zenzai を有効にすると順位は変わらなかった。** Zenzai が神経モデルで
並べ替えるため、学習ストアはその下の格子にしか効かない。

これを [`decisions/0034-zenzai-personalization.md`](decisions/0034-zenzai-personalization.md)
で解決した。`ZenzaiMode.PersonalizationMode` に、確定テキストから学習した
n-gram を渡している。**実測**(`build-and-run-personalization.ps1`):

```
before: 記者の記者 / 汽車の記者 / き者の記者 / 貴社の記者 / 機者の記者
after:  機者の記者 / 記者の記者 / 汽車の記者 / き者の記者 / 貴社の記者
```

「機者の記者」を 40 回確定 → **5位から1位**。残り4件の相対順序は保たれている。

ブロッカーは2つあり、どちらも upstream 依存側のバグだった:

1. **upstream は Windows で個人化を丸ごと除外していた。** 原因とされる
   「SwiftyMarisa が Windows で使えない」の実体は、ヘッダの
   `typedef unsigned long size_t;` **1行**(LLP64 で再定義エラー)
2. **`[Int8]` のキーと検索語を `strlen` で測っていた。** 終端 NUL のない
   Swift 配列なので配列外を読み、同じ trie から実行ごとに違う確率が返っていた
   (0.49297 → 0.125125)。Windows 固有ではなく、単に露見しにくいだけの未定義動作

両方を直した fork をリビジョン固定している。azooKey 側は `Package.swift` の
2箇所のみでソース無改変、fork 点は 0.8.5 タグなので**決定 0028 の
「0.8.5 ↔ llama.cpp b4846 は一体」制約はそのまま維持される。**

- [ ] fork の変更を upstream に PR するかの判断(今は出していない)。
- [x] コールドスタート時に最初の変換が空で返る問題(決定 0033 の範囲)。
      **当初「数秒 IME が死ぬ」と書いたが、実測の結果それは誤りだった。**
      パイプが立つまでは release / debug とも **0.1〜0.4秒**で、失われるのは
      **最初の1変換だけ**、次の打鍵で復帰する — `Connect` が起動後 250ms で
      諦める設計どおりの挙動(打鍵スレッドを止めないことを優先)。
      それでもタダで消せるので、テキストサービスの有効化時にエンジンを起動する
      `EngineClient::Warmup` を追加した。**15ms で戻り、接続は持たない**

### 決定 0034 の再検証 → 解決(改訂あり)

決定 0034 は「学習ストアは Zenzai の順位に届かない」という観測の上に立っている。
その観測は**確認できない状態で行われていた**ことが分かり、測り直した。

原因は2つ重なっていた。どちらも壊れていることが見えない。

1. **`ggml-org/llama.cpp` では zenz モデルを読めない**(日本語 char pre-tokenizer が
   `azooKey/llama.cpp` の fork にしか無い)。読めなくても辞書変換に落ちるので候補は返る
2. **`zenzai_used` はモデルファイルの存在しか見ていなかった**

両方修正のうえ、fork をビルドして Zenzai を本当に動かして測った結果:

| | 3回確定 | 40回確定 |
|---|---|---|
| 学習ストアのみ | 2位 → 2位 | **2位 → 2位** |
| + 個人化(空 base、α=0.15) | 2位 → 2位 | **2位 → 2位** |
| + 個人化(**本物の base**、α=1.0) | 2位 → 2位 | **2位 → 1位** |

- **決定 0034 の前提は正しかった**
- **空 base では個人化も動かない** → 決定 0034 の該当部分を撤回し、base LM を
  インストール時取得にした(`Miwa-Keita/base_n5_lm`、42.6 MB、ライセンス未記載のため同梱はしない)
- **alpha を 0.15 → 1.0**(azooKey-Desktop の既定に合わせる。上限 1.5)

`tsf/Ohagey/tools/build-and-run-learning.ps1` で再現できる。

残る限界(実測):

- [x] **3回の確定では動かない** → **しきい値をコーパス長に比例させて解決。**
      まず訓練コストを実測した(`tsf/Ohagey/tools/build-and-run-training-cost.ps1`、release):

      | 行数 | 時間 | 行数 | 時間 |
      |---|---|---|---|
      | 100 | 66ms | 2,500 | 747ms |
      | 500 | 179ms | 5,000 | 1,317ms |
      | 1,000 | 327ms | 10,000 | 2,652ms |

      数百行から先は線形で約 265µs/行。訓練は毎回コーパス全体を読むので、
      **固定しきい値だと1コミットあたりの CPU が青天井に増える** —
      20 コミットなら新規プロファイルで 3ms/コミット、満杯で 133ms/コミット。
      しきい値をコーパスに比例させるとこれが一定になる。
      `commitsPerTrainingRun(corpusLines:)` = `clamp(lines / 50, 3, 20)`。
      **150行までは3**、1,000行以上は従来どおり20(長く使っている人は従来から悪化しない)。
      新規プロファイルで**3コミット → `generation 1 published (3 lines, 48ms)`** を実測
- [x] ~~**40回確定すると他の候補も入れ替わる**~~ → **そんな限界は無かった。**
      あれもゆらぎ(下記)を見ていたもので、ラティスを毎回作り直すようにした後は
      **どの alpha でも同じ読みの他候補は1件も動かない**(0/19)

#### alpha を測った — 代償は同じ読みの中ではなく**外**に出る

`tsf/Ohagey/tools/sweep-personalization-alpha.ps1`、40回確定。対照
(`PersonalizationEnabled=0` なら昇格しない)が通るようになったので読める。

**しきい値は読みによって違う。1.0 未満は実質何もしない:**

| alpha | `きしゃのきしゃ` | `にほんごのにゅうりょく` |
|---|---|---|
| 0.00 – 0.75 | 2位のまま | 3位 → 2位 |
| **1.00(既定)** | **2位 → 1位** | 3位 → 2位 |
| 1.50 | 2位 → 1位 | **3位 → 1位** |

**問題は触っていない読みに出る。** ハーネスに無関係な読み `あしたのてんき` を足した:

| alpha | 目標 | `あしたのてんき` の1位 |
|---|---|---|
| 0.50 | 効かない | `明日の天気`(無傷) |
| **1.00(既定)** | 2位 → 1位 | **`明日のてんき`** — 正解が2位に落ちる |
| 1.50 | 2位 → 1位 | **`明司多の天気`** — 語ですらない |

**目標を上げる alpha と、無関係な読みを壊さない alpha が重なっていない。**
同じ読みの中だけ見ていると「巻き添え0、いくら上げても無料」に見える。

**ただしこの測定のコーパスは極端**(同じ1文を40行だけ)。実利用のコーパスは多様なので
**被害の上限**であって予測ではない。

- [x] **現実的なコーパスで測り直した。漏れは薄まるが消えない。**
      日常的な82行(`tsf/Ohagey/tools/corpus-sample.txt`)を先に入れ、対照の読みも
      **3つ**にした:

      | コーパス | alpha | 目標 | 触っていない読みが動いた数 |
      |---|---|---|---|
      | 無し | 0.50 | 効かない | 0/3 |
      | 無し | **1.00** | 2位 → 1位 | **3/3** |
      | 無し | 1.50 | 2位 → 1位 | **3/3** |
      | 820行 | 0.50 | 効かない | 0/3 |
      | 820行 | **1.00** | 2位 → 1位 | **2/3** |
      | 820行 | 1.50 | 2位 → 1位 | **1/3** |

      コーパスが豊かになると漏れは減る。規模が出ると alpha は高い方が安全(直感と逆、
      2回反復で同結果)。**ただし効く alpha で漏れ0になる組み合わせは無い** —
      0.5 は無害だが目標も動かない。

一方 `build-and-run-learning.ps1`(個人化 OFF → ON の A/B を1プロセスで回す)は
同じ読み・同じ目標で **2位 → 2位**(動かない)と出る。**2つのハーネスが食い違う。**

潰した仮説:

- [x] ~~ポーリングがゆらぎを拾っている~~ → **変換は決定的**。同じ読みを30回変換して
      差異0件(`tsf/Ohagey/tools/build-and-run-stability.ps1`、新規)
- [x] ~~`n_best` が 20 と 5~~ → どちらでも、個人化 ON/OFF どちらでも昇格する
- [x] **原因はポーリングによる待ち時間そのものだった。** 上の遅延を参照

alpha の話は、まず遅延を片付けてからでないと意味がない。

- [ ] **`alpha=0` は「個人化オフ」と同じではない。** 設定アプリは 0 を選べる
      (決定 0035 の `MinimumAlphaPercent`)ので、0 にしたユーザーが切ったつもりで
      切れていない可能性がある。上が解けたら確認する

#### 決定 0034 の順位変化 → 測り直せるようにした。ただし**「20位→1位」は撤回**

前回ここに「`こうしょう` で20位→1位」と書いたが、**個人化を完全に切っても同じ結果に
なる**ことが後で分かった。確定は変換器自身の学習ストアにも入り、それは格子に効く。
`こうしょう` のような**短い単語**では格子の順序が Zenzai の並べ替えを通り抜けるため、
昇格は本物でも個人化とは無関係だった。**測る読みの選び方を間違えた。**

分離できている測定は `build-and-run-learning.ps1`(個人化 OFF → ON の A/B):

| | 3回確定 | 40回確定 |
|---|---|---|
| 学習ストアのみ | 2位 → 2位 | **2位 → 2位** |
| + 個人化 | 2位 → 2位 | **2位 → 1位** |

**決定 0034 の前提も結論もこれで支持されている。** 数字は地味だがこちらが正しい。
副産物として、**短い読みでは格子が、長い読みでは Zenzai が順位を決める**ことも分かった。

- [x] **`Candidate.reading` が要求した読みのままだった。** `mainResults` には
      入力の一部しか変換しない候補が混ざる(`きしゃのきしゃ` に対する `きしゃ`)。
      `ohagey.proto` は同じフィールドを「部分確定と再学習が使う読み」と定義しているので
      仕様に対するバグ。`Candidate.correspondingCount` から正しく出すようにした
- [x] **ハーネスの目標選択が不健全だった。** `candidates.last` だと断片を全文の読みに
      対して40回教え込むことになる(`記社之記社` が1位に出たのはこれ)。全文を変換して
      いる候補に限定し、かな素通しも除外した。測定に使う読みも `こうしょう` に変更
      (`きしゃのきしゃ` は昇格させられるのが素通し系しか無い)
- [x] **他候補の入れ替わりは「報告」にした。** 既知の限界を FAIL にするとハーネスが
      恒久的に赤になり、常に赤いチェックは誰も読まない

#### ユーザー辞書の語が1位に来ない → **解決(決定 0034 と同じ壁だった)**

登録語には `-10` のコストを与えていて辞書の候補(-14.5 〜 -19)には勝つ。
**それが順位を決めるのは Zenzai が無い間だけ。** Zenzai は格子の上で並べ替えるので、
モデルが載った瞬間にコストは順位を決めなくなる。**実測: Zenzai を切ると1位、
有効にすると3位。**

決定 0036 に記録された「1位」は 2026-07-31 15:46 のもので、**Zenzai が一度も
動いていなかったと判明したのは同日 18:50**。当時、個人化まわりの主張は撤回したが
ユーザー辞書の分を見落としていた。

- [x] **登録語も個人 n-gram に入れる。** Zenzai の順位に届く仕組みはそれしかない。
      コーパスとは別に持ち(コーパスは古い行から捨てられる)、**学習が OFF でも効かせる**
      (自分で辞書に打ち込んだ語は決定 0025 の同意対象である「打鍵の記録」ではない)。
      重みは 40 — 決定 0034 で候補が20位→1位に上がるのに要った実測値。
      **登録直後は候補に出て(格子)、再学習の後に1位へ**という2段構え

- [x] **往復ハーネスが実プロファイルに書き込んでいた。** `build-and-run.ps1` だけ
      `LOCALAPPDATA` を退避しておらず、学習の節が開発者のコーパスに `変換` / `返還` を
      21行入れてモデルまで学習させていた。削除し、スクラッチ方式に統一
