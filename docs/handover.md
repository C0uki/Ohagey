## 3. 🔴 触る前に

### 絶対に守ること(`CLAUDE.md` より)

- **完全オフライン**。インストール時のモデル取得以外、外部通信をしない
- **TSF DLL 側は必ず SEH で例外を握りつぶす**。ホストアプリを落とさない
- **x64 のみ**
- **Zenzai モデルをリポジトリにコミットしない**(CI が守っている)
- パイプはセッション ID 込みの命名 + AppContainer/管理者を許可する ACL

### バージョンは一体で動く

**AzooKeyKanaKanjiConverter 0.8.5 ↔ llama.cpp `b4846` は独立に更新できない。**
片方だけ上げるとリンクエラーになる。

**取得元を `ggml-org/llama.cpp` に変えてはいけない。** 同じタグでも zenz の
日本語 pre-tokenizer が無く、**リンクも起動も変換も通ったまま Zenzai だけが
黙って無効になる**。

## 4. 作業の型 — ここで一番時間を溶かした

一日で**6回**、同じ形で間違えた。**どれも「修正が効かない」に見えて、実際には
そのコードが走っていなかった。**

### 型

```
1. 直す
2. ビルドする
3. インストール／差し替える
4. ★ installed == built をハッシュで確認する ★
5. 新しく起動したアプリで試す
6. tsf.log の module 行でビルドを確認する
```

**4 と 6 を飛ばすと、そのあとの観察は全部無意味になる。**

### なぜ厄介なのか

- **登録済みの TSF DLL は置き換えられない。** テキスト入力面を持つ全アプリに
  読み込まれるので、explorer も含めて掴んでいる。インストーラは
  `restartreplace` で予約し、**再起動で入れ替わる**
  (⚠️ 予約は**サインアウトではなく boot 時**に処理される)
- **エンジンは即座に入れ替わる**(インストーラが `PrepareToInstall` で止める)。
  つまり**更新のたびに「新しいエンジン × 古い DLL」の期間がある**
- **既に動いているアプリは古い DLL を持ち続ける。** 新しく起動したものだけが
  新しいコードを読む。**モジュールのパス表示は改名後も同じ**なので、
  見分けは起動時刻か `tsf.log` でしかつかない

### 再起動を待たずに差し替える

`C:\swb\issout\swap-dll.ps1`(この開発機にある)がやっていること:

> **読み込み中の DLL は削除できないが、改名はできる。** 開いているハンドルは
> ファイルに付いていくので、掴んでいるプロセスは古いコードのまま動き続け、
> 名前だけが空く。新しく起動したアプリが新しいビルドを読む。

出荷経路(インストーラ)は変えていない。**開発中の反復専用。**

## 5. 診断の道具

| ファイル | 中身 |
|---|---|
| `%LOCALAPPDATA%\Ohagey\engine.log` | 起動・設定・**リクエスト1件ごと** |
| `%LOCALAPPDATA%\Ohagey\tsf.log` | TSF 側。**DLL が自分のビルドを1行書く** |

```
module: C:\Program Files\Ohagey\OhageyTSF.dll  282624 bytes  built 2026-08-18 12:04:17
#3 convert (reading 5, preceding 4, n_best 50) -> 50 candidates (zenzai true) in 180ms
#4 commit  (reading 5, text 5, learn true) -> ok in 9ms
```

**どちらも打った内容は書かない。** 読みも候補も確定文字列も入れない —
入れれば、その機械で書かれた文章の平文の記録が、誰も存在を覚えていない
ファイルとして残る。**長さと件数で、ここで問うべきことは全部答えられる。**

`tsf.log` の毎変換の行は `HKCU\Software\Ohagey\DiagnosticLog`(DWORD、既定 0)で
切ってある。**ただし `module:` の1行はスイッチの外**にある —
あれが同じファイルの他の全部の行を信用できるものにしているので、
先に有効化しないと読めない情報にしてはいけない。

### この2つが無かったときの代償

実機の問題を3回、痕跡の無いまま追いかけた。エンジンのログを入れたら
**1回で**原因が出た。TSF のログを入れたときは、**ファイルが存在しないこと自体**が
答えだった(新しいコードが一度も走っていない、と中身を読む前に分かった)。

## 6. 設計の不変条件

この一日で見つかったバグは、**3つとも同じ形**だった:

> **同じ事実を2か所で持ち、片方だけ更新していた。そして間違ったほうを読んでいた。**

| 症状 | 二重に持っていたもの | 直し方 |
|---|---|---|
| 「変換が一回限り」/ 無変換確定が消える | 候補窓の有無を**ポインタと `_candidateMode`** | mode を正とする |
| バックスペースが `おはg` にする | 「1文字」を**打鍵とかな** | **バッファをかなにする** |
| 「修正が効かない」が6回 | ビルドの同一性を**起動時刻と実物** | DLL に自分で名乗らせる |

**片方を捨てて一方を正にする**と、3つとも消えた。3つ目は判定用の関数が
まるごと不要になっている。

### 合成バッファの不変条件

> **解決済みのかな + 未解決のローマ字(末尾)**

未解決部分は**常に末尾の ASCII 連**である(かなは ASCII ではない)。
だから境界を別に覚えておく必要がない。**バッファの1文字が画面の1文字。**

⚠️ **末尾の孤立 `n` はバッファでは `n` のまま。** ん を焼き込むと `hona` が
ほな にならない。表示と読みだけが ん に閉じる。

## 7. 既知の限界(⚠️ を読まずに触らないこと)

- 🔴 **AppContainer はエンジンを起動できない。** `CreateProcess` が禁じられている。
  エンジンが落ちていると UWP アプリでは**打てるのに変換だけ効かない**
  (**エラーにならない** — 接続失敗を「候補なし」として扱うため)。
  だから `idleTimeoutSeconds` の既定を **0(常駐)** にしてある
- ⚠️ **無変換確定は学習の半分にしか届かない。** コーパスには入るが、
  **変換器の学習ストアには入らない** — 渡せる `Candidate` が存在しないため
- ⚠️ **個人化オンだと確定した語句の控えが平文で残る**(`personal/corpus.txt`)。
  切れば消える(決定 0025)
- ⚠️ **個人モデルは base から resume しないと害になる。** ゼロから学習すると
  無関係な30件中15〜18件が正解を失う。**resume 可能な base が無ければ
  適用しないガードがある**ので、取得に失敗した端末では既定オンでも何も起きない
- ⚠️ **`kyo` のような音節はバックスペースで きょ→き になる**(いまは正しい)。
  以前の実装では `k` まで戻った。バッファをかなにしたので直っている
- ⚠️ **重複除去をコーパスに入れてはいけない。** 繰り返し確定したこと自体が
  個人化の読む信号で、昇格には3〜40回要る。Tuner が MinHash で落とすのは
  画面収集の副産物であって頻度ではない
- 🔴 **出荷する GPU バックエンドは vulkan。** 22.6MB で cuda(977MB)と同じ速さ、
  しかも GPU を選ばない(cpu 195ms / cuda 147ms / vulkan 150ms)
