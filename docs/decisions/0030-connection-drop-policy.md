# 0030: 壊れたリクエストを受け取ったときに接続を切るかどうか

## 背景

名前付きパイプの接続は**ホストアプリ1つにつき1本**(決定 0004 / 0006)。
つまり接続を切ることは、そのアプリにとって「IME が一瞬消える」ことに等しい。
再接続はできるが、**合成中の未確定文字列は失われる**。

一方で、何を受け取っても接続を維持し続けるわけにもいかない。フレームの区切りを
見失った状態で読み続ければ、以降のバイト列をすべて誤って解釈することになる。

「クライアントが送ってきたものが壊れていた」には性質の異なる3つがあり、
それぞれ取れる手が違う。

## 決定事項

| 状況 | 対応 | 理由 |
|---|---|---|
| **unservable** — Protobuf としてはパースできたが、エンジンが処理できない(oneof 未設定、`reading` が空 等) | **同じ `request_id` で `failure` を返し、接続は維持** | `request_id` が取れているので、クライアントは応答をリクエストに対応付けられる。1件の不正リクエストのために、合成中のアプリから IME を奪う理由が無い |
| **malformed** — Protobuf のパース自体に失敗。`request_id` が取れない | **接続を切る** | 返すべき ID が無い。`request_id = 0` で返すと、パイプライン化しているクライアントには**送っていないリクエストへの応答**に見え、対応付けを壊しかねない。黙って切る方が誤解が無い |
| **framing error** — 長さプレフィックスが上限を超える等、フレーム境界を信用できない | **接続を切る** | 次のフレームがどこから始まるか分からない。**復帰先が存在しない**ので、切る以外の選択肢が無い |

## なぜ unservable だけ特別扱いするのか

スキーマが前に進んだときに効いてくる。クライアントが新しい `oneof` のケースを
送ってきた場合、こちらのビルドではそれは「ケースが1つも設定されていない」として
到着する(proto3 の仕様)。これを malformed と同じ扱いにすると、**新しいクライアントが
古いエンジンに繋いだ瞬間に接続を切られる**ことになる。

`failure` を返して接続を維持しておけば、クライアントは「このリクエストは通らない」と
判断して古い形式にフォールバックできる。IME が動かなくなるのと、1機能が使えないのとでは
ユーザーへの影響がまるで違う。

## 実装

`WireDecodeFailure`(`engine/Sources/OhageyEngineProto/WireMapping.swift`)が
`unservable(requestID:error:)` と `malformed(underlying:)` を**型として区別**している。
`request_id` を持つかどうかがそのまま「応答できるかどうか」なので、呼び出し側が
判断を間違えにくい。

framing error は `FramingError`(`OhageyEngineCore/Framing.swift`)として別経路で
上がってくる。接続を捨てる処理は `PipeConnection.serve()` にある。

## 実機で確認済み

`request_id = 99` の oneof 未設定リクエストに対し、
`request_id = 99` / `CODE_INVALID_ARGUMENT` / `"request kind is not set"` を返し、
**同じ接続で続けて送った `Ping` に正常応答すること**を確認した。
