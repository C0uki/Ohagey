# 決定 0034: 学習を Zenzai の順位に効かせる

決定 0025(学習はデフォルト有効)の実装に必要だった未確定部分。
決定 0021(依存コードの取り込み方)に fork という選択肢を追加する。

## 背景 — 学習していたのに、順位が変わっていなかった

`commit` は `updateLearningData` を呼んで変換器の学習ストアを埋めている。
これは**辞書のみのときは効く**が、**Zenzai を有効にすると効かない**。実測:

| モデル | 2番目の候補を確定 → 再変換 |
|---|---|
| なし(辞書のみ) | 1位に上がる |
| あり(Zenzai) | 順位は動かない |

学習ストアはラティスを養う。Zenzai はそのラティスの**上**でニューラルモデル
による再ランクをかける。つまり学習は届いていない。

upstream が Zenzai 自体を個人化する手段は
`ZenzaiMode.PersonalizationMode` で、学習済みの n-gram 言語モデル 2本
(base と personal)を marisa trie として受け取る。

## 障害だったもの

**upstream は Windows で個人化を丸ごと除外していた。**

```swift
#if (!os(Linux) || !canImport(Android)) && !os(Windows)
// Android環境・Windows環境ではSwiftyMarisaが利用できないため、EfficientNGramは除外する。
```

除外されると `EfficientNGram` はモック実装になり、全語に一律 `1/6000` を返す。
`trainNGram` はそもそも宣言すらされない。

理由とされる「SwiftyMarisa が Windows で利用できない」を確かめたところ、
**原因はヘッダの1行だった**:

```c
typedef unsigned long size_t;   // <stdlib.h> の直後にある
```

Windows x64 は LLP64 で `size_t` は `unsigned long long`。`unsigned long` は
32bit なので再定義エラーになる。これはどのプラットフォームでも本来バグで、
たまたま `unsigned long == size_t` の環境では露見しなかっただけ。

その1行を消すと **`swift build` が通り、機能テストも全部通った** —
構築・検索・predictive/prefix・save/load の往復。

### さらに見つかった、もっと深いバグ

ビルドが通ることと動くことは別だった。学習後の `bulkPredict` が
**実行ごとに違う値を返した**:

```
実行1: bulkPredict("おはぎー") の最大 = 0.49297109375
実行2: 同じ trie ファイル、同じクエリで 0.125125
```

`marisa_add_word` と `marisa_search` は `const char *` を取って `strlen` する。
String から呼ぶ分には正しいが、SwiftyMarisa の **`[Int8]` オーバーロードは終端
NUL のない Swift 配列をそのまま渡していた**。EfficientNGram はキーの区切りに
負値を使う設計でキー部分に 0 が現れないため、`strlen` は必ず配列を踏み越え、
その先のメモリがキーと検索語の一部になっていた。

長さを取る `marisa_add_word_l` / `marisa_search_l` を足し、`[Int8]` 版から
そちらを呼ぶようにした(`marisa::Keyset::push_back` と
`marisa::Agent::set_query` はどちらも長さ付きオーバーロードを持っている)。
以後、同じ 3 実行が `0.496046240234375` で完全に一致する。

**このバグは Windows 固有ではない。** 未定義動作なので、配列の直後がたまたま
0 になりやすい環境では表面化しにくいだけ。

## 決定

### 1. fork を切ってコミットで固定する

| リポジトリ | fork | 変更内容 |
|---|---|---|
| `ensan-hcl/SwiftyMarisa` | [`C0uki/SwiftyMarisa`](https://github.com/C0uki/SwiftyMarisa) `ohagey-windows` | `size_t` 再定義の削除、`[Int8]` 経路への長さ引き渡し |
| `azooKey/AzooKeyKanaKanjiConverter` | [`C0uki/AzooKeyKanaKanjiConverter`](https://github.com/C0uki/AzooKeyKanaKanjiConverter) `ohagey-windows` | `Package.swift` のみ2箇所。Windows 除外の解除、`EfficientNGram` の product 公開 |

**azooKey 側はソース無改変**。fork 点は 0.8.5 タグそのものなので、
**決定 0028 の「0.8.5 ↔ llama.cpp b4846 は一体」という制約はそのまま維持される。**

ブランチではなく**リビジョンで固定**する。ブランチ指定だと再現性がない。

`EfficientNGram` を product として公開する必要があるのは、
`PersonalizationMode` が学習済み trie を受け取るだけで**それを作る手段を
提供しない**ため。`trainNGram` はこのターゲットにある。

upstream への PR は今回は出さない。fork で運用して確かめてから判断する。

### 2. base 言語モデルは同梱せず、空の trie で代替する

upstream の base n-gram LM は Hugging Face で配布されているが、
**ライセンスが明記されていない**。再配布できないし、決定 0016 により
インストール時以外の通信もできないので、実行時取得もできない。

そこで**何も学習していない base**を初回起動時に生成して置き換える。

これは劣化というより意味の変化である。`ZenzContext` の混合は

```
logit += alpha * (log p_personal - log p_base)
```

なので、**base が全語に同じ値を返すなら、全語に同じ定数を足すだけになり
順位は動かない**。実測: 空 base は 6000 語すべてに `1/6000` を返す(spread 0.0)。
結果として、ユーザーが打ったことのない候補は **Zenzai がつけた順序をそのまま
保ち**、学習した候補だけがそこから持ち上がる。

実測でも確認した。「機者の記者」を 40 回確定させた後:

```
before: 記者の記者 / 汽車の記者 / き者の記者 / 貴社の記者 / 機者の記者
after:  機者の記者 / 記者の記者 / 汽車の記者 / き者の記者 / 貴社の記者
```

ターゲットが 5位→1位 に上がり、**残り4件の相対順序は完全に保たれている。**

代償は較正である。打ち消してくれる本物の base が無い分、同じ alpha が
はるかに強く効く。

| alpha | 頻出語への加点 | 未学習語 |
|---|---|---|
| 0.50 (upstream 既定) | **+4.00 logits** | -2.38 |
| 0.25 | +2.00 | -1.19 |
| **0.15 (Ohagey 既定)** | **+1.20** | -0.72 |
| 0.10 | +0.80 | -0.48 |

upstream 既定の 0.5 はニューラルモデルを丸ごと押し切ってしまう。
**既定を 0.15 とし、設定で変更可能**にする。

### 3. コーパスを持ち、毎回まるごと学習し直す

確定したテキストを `%LOCALAPPDATA%\Ohagey\personal\corpus.txt` に1行ずつ
追記し、20コミットごとにコーパス全体から再学習する。

差分学習(`resumeFilePattern`)ではなく全体再学習にした理由:

- **決定 0025 の「消せる」が本当に成立する。** trie からエントリを引き算する
  必要がなく、ファイルを消すだけで済む
- 破損やドリフトが蓄積しない
- **そもそも安い。** 実測 10,000行で 1.8秒、ディスク 50 KiB。
  差分学習も既存 trie 全体を読み直すので、大きな差はない

コーパスは 10,000行で頭打ちにする(古い順に捨てる)。再学習コストと、
「打った内容がどこまで遡って残るか」の両方に上限をかけるため。

### 4. 世代ディレクトリで差し替える

**欠けた trie や書きかけの trie を読むと、エラーにならずプロセスが落ちる。**
実測 `0xC0000409`。marisa が C++ から throw し、エンジンの main までの間に
受ける者がいない。

なので再学習は変換器が読んでいるかもしれないファイルを**絶対に上書きしない**。

```
personal/
  corpus.txt
  base_*.marisa          ← 一度作ったら置き換えない
  gen-3/model_*.marisa   ← 現行世代
  gen-4.partial/         ← 学習中。ディレクトリ名が世代として parse されない
```

`gen-4.partial` に書き切ってから、**ディレクトリごと** `gen-4` に move する。
読み手からは「前の世代がまるごと見える」か「新しい世代がまるごと見える」かの
どちらかで、途中は見えない。新世代を公開してから旧世代を消す。

起動時は**番号の大きい順に、5ファイル揃っているものを探す**。
最大の番号を信用しないのは、ディレクトリを作った直後に落ちた実行があると
それを掴んでしまい、掴んだ瞬間に落ちるため。

### 5. 学習を切ったら記録も消す

`personalizationActive = learningEnabled && personalizationEnabled`。

個人化は変換器の学習ストア(不透明なデータベース)と違い、**確定した語句を
平文でディスクに置く**。性質が違うので設定も分けたが、
**学習を切れば個人化も切れる**(逆はない)。

そして切り替えを検知したらコーパスと学習済み世代を**消す**。共有端末で
学習を切る人は「もう見に行かない」ではなく「残さない」を求めている
(決定 0025)。

## 検証

`tsf/Ohagey/tools/build-and-run-personalization.ps1`

自分のプロファイルを汚さないよう、`LOCALAPPDATA` をスクラッチに向けてから
エンジンを起動する(エンジンは環境を継承する)。既にエンジンが動いていると
本物のプロファイルを掴んでいるので、その場合は実行を拒否する。

`swift test` は 107件パス(個人化まわりで +25)。

## 副産物として分かったこと

`EngineClient::Connect` の再試行は約1秒で、エンジンのコールドスタート
(辞書 + Zenzai の重み)はそれより明らかに長い。**再起動後の最初の変換が
空で返り、次の打鍵で通る**可能性がある。ハーネス側は待つようにしたが、
TSF クライアント本体は未対応。決定 0033 の範囲なので別途。

# 改訂(2026-08-01): base LM を入れる

**上の「2. base 言語モデルは同梱せず、空の trie で代替する」は撤回する。**
空 base での個人化は、実測すると**機能していなかった**。

## なぜ気付けなかったか

2つの不具合が重なっていた。どちらも「壊れていることが見えない」種類のもの。

1. **`ggml-org/llama.cpp` では zenz モデルを読めない。** 日本語 char pre-tokenizer は
   `azooKey/llama.cpp` の fork にしか無い。読めなくてもエンジンは辞書変換に落ちるので、
   候補は返り続ける。
2. **エンジンの `zenzai_used` はモデル**ファイルの存在**しか見ていなかった。**
   llama が読めたかは見ていない。

結果、**上の検証はすべて Zenzai が動いていない状態で行われていた**。
「5位→1位」も、当時は Zenzai の再ランクではなく別の経路で起きていた。

両方修正した(`docs/local-setup.md` と `ConversionService.noteZenzaiStatus`)。

## Zenzai を本当に動かして測り直した結果

読み `きしゃのきしゃ`、2位の候補 `貴社の記者` を確定する。

| | 3回確定 | 40回確定 |
|---|---|---|
| 学習ストアのみ(個人化オフ) | 2位 → 2位 | **2位 → 2位** |
| + 個人化(空 base、α=0.15) | 2位 → 2位 | **2位 → 2位** |
| + 個人化(**本物の base**、α=1.0) | 2位 → 2位 | **2位 → 1位** |

- **決定 0034 の前提は正しい。** 学習ストアだけでは、40回確定しても Zenzai の順位は動かない
- **空 base では個人化も動かない。** これがこの改訂の理由
- **本物の base があれば動く**

## base LM は実在し、入手できる

azooKey-Desktop の `.gitmodules`:

```
[submodule "azooKeyMac/Resources/base_n5_lm"]
	url = https://huggingface.co/Miwa-Keita/base_n5_lm
```

`lm_c_abc` / `lm_r_xbx` / `lm_u_abx` / `lm_u_xbc` の4ファイル、計 42.6 MB。
**`_c_bc` は無い** — あれは学習を再開するときだけ要るもので、推論には要らない。

**ライセンスは依然として未記載。** なので**同梱はしない**。zenz の重みと同じ扱いで、
インストール時に元の場所から取得する(決定 0008 の経路)。azooKey-Desktop も
submodule として参照しているだけで、リポジトリには入れていない。

## alpha は 0.15 → 1.0

azooKey-Desktop の設定値(同じ変換器・同じ base LM を使う):

| | alpha |
|---|---|
| off | 0 |
| soft | 0.5 |
| **normal(既定)** | **1.0** |
| hard | 1.5 |

当初の 0.15 は**実測ではなく推論で決めた**値だった。「base が無い分、同じ alpha が
強く効くはずだから小さくする」という理屈で、方向としては合っていたが、
**空 base の問題は強さではなく、そもそも比較対象が無いこと**だった。

上限も 1.0 → 1.5 にした。azooKey-Desktop の "hard" を黙って頭打ちにしないため。

## 残る限界(実測で見えたこと)

- ~~**3回の確定では動かない。**~~ → **下の追記で解決**
- **40回確定すると、他の候補も入れ替わる**(元の4件のうち残ったのは1件)。
  個人化は依然として粗い

## 追記(2026-08-01)— 再学習のしきい値をコーパス長に比例させる

「3回の確定では動かない」を直した。しきい値 20 は測って選んだ値ではなかったので、
まず訓練コストを実測した(`tsf/Ohagey/tools/build-and-run-training-cost.ps1`、release):

| 行数 | 時間 | 行数 | 時間 |
|---|---|---|---|
| 100 | 66ms | 2,500 | 747ms |
| 500 | 179ms | 5,000 | 1,317ms |
| 1,000 | 327ms | 10,000 | 2,652ms |

数百行から先は**線形**で、約 265µs/行。

訓練は毎回コーパス全体を読む。だから**固定しきい値は「1コミットあたりの CPU が
使い込むほど増える」**ことを意味する — 20 コミットなら新規プロファイルで
3ms/コミット、コーパス満杯で 133ms/コミット。しきい値をコーパスに比例させれば
これが一定になる。

```
commitsPerTrainingRun(corpusLines) = clamp(corpusLines / 50, 3, 20)
```

- **150行までは 3。** 「同じ誤変換を3回直した」が効く。新規プロファイルで
  **3コミット → `generation 1 published (3 lines, 48ms)`** を実測
- **1,000行以上は 20。** 長く使っている人は従来から悪化しない
- 引き換えに、長く使っている人は最大20コミット待つ状態に戻る。その人のモデルは
  既に多くを知っているので1件の追加が動かす量は小さく、代わりに払うのは
  「入力中に CPU の大半を再学習に使う」ことになる

### 途中で見つけた欠陥 — CRLF のコーパスが1行に潰れていた

`readCorpus()` が `split(separator: "\n")` を使っていた。**Swift では `"\r\n"` は
1つの `Character`** であり `"\n"` と等しくないので、**CRLF のファイルは全く分割
されない**。980行のコーパスが1行として読まれるのを実測した。

エラーにならず、空にも見えず、症状は「個人化が入力を反映しなくなる」だけ。
エンジン自身は LF で書くので、これは**他の何かがファイルに触ったとき**に起きる —
決定 0025 が招いている「IME が自分について何を覚えているか見に行く」がまさにそれ。
`split(whereSeparator: \.isNewline)` に変更し、`PersonalizationLayout.corpusLines`
としてテスト可能な場所へ出した。

### ⚠️ このとき、決定 0034 の順位変化が**再現しないことが分かった**

`build-and-run-personalization.ps1` が2件とも FAIL する。候補一覧そのものが
記録と違う:

```
記録: 記者の記者 / 汽車の記者 / き者の記者 / 貴社の記者 / 機者の記者
現在: 記者の記者 / キシャノキシャ / きしゃのきしゃ / きしゃ / 期しゃ
```

**上記のしきい値変更が原因ではない。変更前の `main` でも同じ結果になる**ことを
確認済み。`ZenzaiInferenceLimit`(1/5/10/30)でも、空のユーザー辞書の
`importDynamicUserDict([])` でもなかった。

分かっているのは2点で、どちらも未解決:

1. `mainResults` に**部分長の候補**が混ざる(`きしゃ` / `期しゃ` は
   `きしゃのきしゃ` 全体の変換ではない)。IME としては候補窓に断片が並ぶ
2. ハーネスが `candidates.last` を目標にしているため、**断片を全文の読みに対して
   40回教え込む**ことになる。実際 `記社之記社` という無意味な候補が1位に出た。
   候補の実際の読みで絞りたいが、`EngineCandidate.reading` には
   **要求した読みがそのまま入っている**(`ConversionService.convert`)ので
   今は区別できない

決定 0034 の結論(本物の base LM + α=1.0 で順位が動く)を撤回するものではない。
**測り直せる状態に戻す作業が残っている**、というのが現状。

## 追記(2026-08-01、その2)— 測り直せるようにした。結論は保たれている

上の2点を直した結果、**決定 0034 の主張は再現する。しかも以前より強い形で。**

```
before: 高商 / 高唱 / 交渉 / 高尚 / 公称 …(20件)
target: 康尚 — 20位
after:  康尚 / 交渉 / 高尚 / 公称 / 考証 …
target: 20位 → 1位
```

40回の確定で **20位の候補が1位になる**(以前の記録は5位→1位)。

### 直したもの1 — `Candidate.reading` が要求した読みのままだった

`ConversionService.convert` が全候補に**要求した読みをそのまま**入れていた。
`ohagey.proto` は同じフィールドを「部分確定と再学習が使う読み」と定義しているので、
これは仕様に対する明確なバグ。

`mainResults` には**入力の一部しか変換しない候補**が混ざる
(`きしゃのきしゃ` に対する `きしゃ` / `期しゃ`)。これは日本語 IME として正常な
挙動で、upstream は各候補が何文字に対応するかを `Candidate.correspondingCount` で
持っている。エンジンは `.direct` で合成しているので、要求した読みの
`prefix(correspondingCount)` がそのまま候補の読みになる。

これを間違えると、クライアントは**候補が変換していない合成文字列を確定してしまい**、
学習には「`きしゃのきしゃ` は `期しゃ` と読む」と教わることになる。実際そうなっていた。

### 直したもの2 — ハーネスが断片を目標にしていた

`candidates.last` を目標にしていたので、部分長候補が入った瞬間に**断片を全文の読みに
対して40回教え込む**測定になっていた(`記社之記社` が1位に出たのはこれ)。
候補の読みが正しくなったので、**全文を変換している候補**に限定できる。

読みそのもの(かな素通し)も除外する。全長候補ではあるが、個人化はまさにその文字列で
学習した文字 n-gram なので、上がって当たり前で何も示さない。

測定に使う読みも `きしゃのきしゃ` → **`こうしょう`** に変えた。前者は全長候補が
「1位の漢字・片仮名・かな素通し」しかなく、昇格させられるのが素通し系だけだった。
`こうしょう` は20件すべてが別の語になる。

### 他候補の入れ替わりは「報告」にした

「確定していない候補まで並び替わる」のは決定 0034 が既に記録している**既知の限界**で、
ロードマップも未解決として持っている。これでハーネスを FAIL にすると恒久的に赤になり、
**常に赤いチェックは誰も読まない**ので、守りたかったものが守られなくなる。

断言するのは「確定した候補が上がる」だけにし、巻き添えの量は数字付きで出力する。
`こうしょう` では実際に起きる(1位の `高商` が `交渉` の下へ)。

### ⚠️ 別件が1つ未解決のまま残った — ユーザー辞書の語が1位に来ない

`build-and-run-userdict.ps1` が失敗する。登録した語は候補には出るが**3位**で、
決定 0036 の記録(1位)と違う。

```
after: おはぎー / おはギー / Ohagey / おは / オハギー
```

**本 PR が原因ではない**(未変更の `main` で確認)。潰した仮説:

- 個人化 — 世代が無ければ `personalizationMode` は nil を返すので効いていない
- `OHAGEY_BASE_LM_PATH`(本物の base LM)の有無 — どちらでも3位

# 追記(2026-08-01、その5)— 追記4を撤回する。**前提は崩れていなかった**

追記4で「学習ストアは Zenzai の順位に届く。約15秒かかるだけ」と書いた。**撤回する。**
あれは**候補順のゆらぎを都合よく拾っていた**だけだった。

## 実際に起きていたこと — 変換ごとに候補順が入れ替わっていた

確定した後、同じ読みを**間に何も挟まず5回連続で**変換すると:

```

```

**同じ入力に対して、呼ぶたびに違う順序が返っていた。** 追記4の「15秒後に1位」も、
個人化ハーネスの「最大30秒ポーリング」も、この振動の山を掴んでいただけである。
「時間が経つと効く」ではなく「奇数回目と偶数回目で違う」だった。

先に確かめておいた「変換は決定的」(追記3)は**確定を挟まない**場合の話で、
確定の後は成立していなかった。

## 原因 — 前の変換のラティスを引き継いでいた

`requestCandidates` は前回のラティスと Zenzai のキャッシュを保持し、次の要求が
前回の続きに見えるときは再利用する。**1打鍵ずつ渡すキーボードには正しく、ここでは
間違っている** — ワイヤ上の1要求は読み全体を運ぶので(決定 0007)、引き継ぐべき
続きは存在せず、古い状態を引き継ぐだけになる。

`ConversionService.convert` の先頭で `converter.stopComposition()` を呼ぶようにした。
**同じ場所を、同じ理由で、既に2箇所が呼んでいた**(`commit` とユーザー辞書の適用)。
気付いた人がその都度パッチを当てていたものを、規則にした。

## 直した後の測定

```
学習ストアのみ・3回確定:   2 2 2 2 2   → 2位のまま
学習ストアのみ・40回確定:  2 2 2 2 2   → 2位のまま
+ 個人化・3回確定:         2 1 1 1 1   → 1位(2回目で再学習が公開された)
+ 個人化・40回確定:        1 1 1 1 1   → 1位
```

**決定 0034 の前提も結論も、元のとおり正しい。** 学習ストアだけでは Zenzai の順位は
動かず、個人化を足すと動く。他の候補4件も全て残っている。

3回確定の2回目で切り替わるのは、再学習が非同期に公開されるため(追記1のしきい値)。
これは仕様どおりで、振動ではない。

## 代償 — 変換が遅くなる

キャッシュが効かなくなるので、毎回ラティスを作り直す。release / CPU、
`きしゃのきしゃ`(7モーラ)で **平均 137ms、最悪 191ms**
(`tsf/Ohagey/tools/build-and-run-stability.ps1`)。

以前の記録は p50 70〜95ms だが、`docs/local-setup.md` が警告しているとおり
**素朴に測るとキャッシュを測ってしまう**。137ms の方が、ユーザーが実際に払う値に近い。

**この取引は正しいと考える。** 候補窓が呼ぶたびに並び替わる IME は、少し遅い IME より
はるかに悪い。ユーザーは「2番目を選ぶ」という手癖を作れなくなる。
ただし**数字が数字なので、判断は残しておく** — 速度を優先するなら、
「同じ読みが連続したときだけキャッシュを捨てる」といった折衷もありうる。

## 教訓

同じ入力を1回しか測らないと、振動しているものを「効かない」とも「効く」とも読める。
**決定 0034 の元の観測(「順位は動かない」)も、追記4(「15秒で動く」)も、
どちらも1点しか見ていなかった。** 連続で複数回測るのは、それ自体が対照実験である。
