# 決定 0036: ユーザー辞書のフォーマット

決定 0026(明示的なユーザー辞書登録を初期スコープに含める)の未確定部分。
これが決まらないため `registerWord` はずっとエラーを返していた。

## 決定: タブ区切りテキスト

`%LOCALAPPDATA%\Ohagey\userdict.tsv`(決定 0024 のユーザーごとのデータ配下)

```
#!ohagey-userdict 1
おはぎー	Ohagey	propernoun
たなか	田中	surname
```

| 列 | 内容 |
|---|---|
| 1 | 読み(かな) |
| 2 | 変換後の語 |
| 3 | 品詞(省略時は `noun`) |

`#` 始まりの行はコメント。1行目のバージョン表記もコメントの形にしてある。

品詞は ASCII の固定キー: `noun` / `propernoun` / `personname` / `surname` /
`givenname` / `organization` / `placename` / `symbol`。

### JSON にしなかった

**JSON は構文エラー1つで全エントリを失う。** このファイルには、ユーザーが何年か
かけて手で入れた語が数千件入りうるし、手編集も想定される。ひらがな1文字の打ち間違いで
全部消えるのは受け入れられない失敗の仕方ではない。

行指向なら**壊れた行だけ**を失う。これは決定 0035 で設定の壊れた値に対して決めた
規則と同じ考え方である。

副次的に、将来他 IME からのインポート(決定 0027)を拾う場合も安くなる。
MS-IME も Google 日本語入力もタブ区切りテキストで書き出す。

## 品詞 ID はファイルに書かない

変換器が要求するのは `cid` / `mid` という数値 ID である。これをそのまま書くと
`1289` だらけの読めないファイルになり、しかも **upstream のバージョンで変わりうる**。

ファイルには Ohagey の名前を書き、ID への対応付けは変換器の隣(`UserDictionaryStore`)に
置く。ユーザーの辞書ファイルの中身が upstream の内部テーブルに依存しないようにする。

| Ohagey | CIDData | MIDData |
|---|---|---|
| `noun` | 一般名詞 | 一般 |
| `propernoun` | 固有名詞 | 一般 |
| `personname` | 人名一般 | 一般 |
| `surname` | 人名姓 | 人名姓 |
| `givenname` | 人名名 | 人名名 |
| `organization` | 固有名詞組織 | 組織 |
| `placename` | 地名一般 | 一般 |
| `symbol` | 記号 | 一般 |

## LOUDS ではなく実行時インポートを使う

変換器は `sharedContainerURL` の `user.louds` / `user.loudschars2` を読む。
しかしそれを作る `LOUDSBuilder` は upstream の **CLI ターゲット**にあり、
ライブラリとして公開されていない。エンジンからは呼べない。

`importDynamicUserDict` はメモリ上のエントリをそのまま受け取り、コンパイル手順が要らない。
upstream 自身の評価コマンドもこちらを使っている。

## 実装で踏んだこと(3つとも実測で分かった)

### 1. `ruby` はカタカナでなければならない

`getMatchDynamicUserDict` は `ruby` の**完全一致**で引く。そして変換器は照合キーを
`character.toKatakana()` で組み立てる(`getRanges` の最後でも `.toKatakana()` する)。

ひらがなのまま渡すと**エラーにならずに黙って一致しない**。切り分けた実測:

```
ruby=オハギー: Ohagey / おはぎー / オはぎー / ...   → 出る(1位)
ruby=おはぎー: おはぎー / オはぎー / ...            → 出ない
```

### 2. 辞書を入れ替えたら `stopComposition()` が要る

**これが一番時間を食った。** `requestCandidates` は直前のラティスをキャッシュし、
次の要求が継続入力に見えるときは再利用する。

そのため「登録 → 同じ読みをもう一度変換」は、**登録前に作られたラティスから答えが返る**。
エントリはストアに入っていて、ストアは引かれていて、それでも候補に出ない。

学習側は同じ罠を踏むので `commit` で `stopComposition()` を呼んでいる
(そのコメントも書いてあった)。ユーザー辞書の入れ替えでも同じことをする。

### 3. コストは -10

upstream の動的ユーザー辞書が使う値。組み込み候補は -14.5 〜 -19 で、値は負で
0 に近いほど強い。つまり**明示的に登録した語は辞書の推測に勝つ**。登録した意味がそこにある。

## 壊れた値の扱い

決定 0035 と同じ規則。**壊れた行はその行だけ**落とし、残りは読む。

| 状況 | 扱い |
|---|---|
| タブが足りない行 | その行だけ飛ばす。行番号をログに出す |
| 品詞が未知の名前 | `noun` に倒して**語は残す**(新しい設定アプリかもしれない) |
| 品詞の列が無い | `noun` |
| 列が多い | 知っている列だけ読む(将来のフォーマット) |
| 読みと語が同じ行の重複 | 1つにまとめる(同じ候補が2つ並ぶため) |
| 同じ読み・違う語 | **両方残す**。ユーザー辞書の本来の用途 |

読みが**かな以外**のときは登録を拒否する(`INVALID_ARGUMENT`)。引き当ては
かなで行われるので、漢字の読みは**読み込めるが決して一致しない**。よくある間違いは
読みの欄に語を入れてしまうことなので、ダイアログを見ている間に言う方がよい。

書き出すときはタブと改行を空白に**置換**する。エスケープ規則を作ると、手で編集する人が
覚えることが増える。読みにも語にもこの2文字は入らない。

## 設定アプリが直接編集する

設定アプリはこのファイルを直に読み書きする(決定 0013)。エンジンは**変換のたびに
mtime を見て**、変わっていれば読み直す。

設定監視のような別スレッドの通知機構を足していない。`stat` 1回は変換の前では無に等しく、
通知を取りこぼす経路が無く、仕組みが1つ増えない。

## 検証

`tsf/Ohagey/tools/build-and-run-userdict.ps1`(Zenzai 有効のまま)

```
before: おはギー / 尾羽ギー / オハギー / オはギー / 尾はギー
after:  Ohagey / おはギー / 尾羽ギー / オハギー / オはギー
```

漢字の読みは `INVALID_ARGUMENT` で拒否され、**接続は維持される**(決定 0030)。

`swift test` **136件パス**。

## ハーネス側で見つけた不具合(同時に修正)

個人化ハーネス(決定 0034)とこのハーネスは、冒頭で「エンジンが既に動いていないか」を
`EngineClient::Connect` で確かめていた。**`Connect` は動いていなければ起動する**
(決定 0015 / 0033)。`LOCALAPPDATA` をスクラッチに向ける**前**に呼んでいたため、
実プロファイルでエンジンが立ち上がっていた。

パイプを直接開く形に変えた。実際にテスト用の単語が実プロファイルに書かれていたので
削除済み。
