# 決定 0035: 設定スキーマの確定

決定 0014(設定変更の反映方法)は「レジストリ**または**設定ファイル」と両論併記の
まま止まっていた。設定アプリ(決定 0013)を書き始める前に決める必要がある。

## 決定: HKCU のレジストリ

```
HKEY_CURRENT_USER\Software\Ohagey\
```

| 値名 | 型 | 範囲 | 既定 | 意味 |
|---|---|---|---|---|
| `SchemaVersion` | REG_DWORD | — | 1 | 設定アプリが書く。無ければ 1 とみなす |
| `LearningEnabled` | REG_DWORD | 0 / 非0 | 1 | 決定 0025 |
| `PersonalizationEnabled` | REG_DWORD | 0 / 非0 | 1 | 決定 0034 |
| `PersonalizationAlphaPercent` | REG_DWORD | 0〜100 | 15 | 決定 0034。**パーセント** |
| `Backend` | REG_SZ | `cpu` / `cuda` / `vulkan` | `cpu` | 決定 0010 / 0028。大文字小文字は問わない |
| `ZenzaiInferenceLimit` | REG_DWORD | 1〜100 | 10 | 1リクエストあたりの推論ステップ上限 |
| `IdleTimeoutSeconds` | REG_DWORD | 0〜86400 | 300 | 決定 0015。**0 は監視の無効化** |

**ユーザーごと(HKCU)であって、マシン共通(HKLM)ではない。** これらは好みであり、
そのうちの1つは「打った内容を覚えるかどうか」を決める(決定 0025)。
あるアカウントが別のアカウントの分まで決めてよい設定ではない。

エンジンは**この場所に値を書かない**。書くのは設定アプリだけ。

### ファイル方式を採らなかった

`%LOCALAPPDATA%\Ohagey\settings.json` + `ReadDirectoryChangesW` は既に実装され、
ホットリロードまで実機検証済みだった。それを捨てている。

理由は Windows の IME としての慣例(MS-IME / Google 日本語入力はいずれもレジストリ)と、
将来グループポリシーで一括配備する余地を残すこと。

代償: `OhageyEngineCore` に Windows 依存が入りかねない。これは**分割で回避した**
(下記)。

## パーセントで持つ理由

`PersonalizationAlphaPercent` だけ、モデル上の型(`Double` の 0.0〜1.0)と
保存形式(0〜100 の整数)が違う。

レジストリに浮動小数点型は無い。`REG_SZ` に `"0.15"` と書く手もあるが、それは
**ユーザーと「IME が動くかどうか」の間に小数のパースとロケール問題を挟む**ことになる。
alpha の有効範囲は 0.10〜0.25 程度で、1%刻みは必要以上に細かい(決定 0034 の実測)。

## 壊れた値の扱い

**欠けている値・型違い・範囲外は、その項目だけを既定値または最近傍に倒す。**
セット全体を拒否しない。

拒否は privacy bug になる。1つの値が壊れているせいで全体を既定値に戻すと、
**学習をオフにしていたユーザーが黙ってオンに戻る**(決定 0025)。これは
この設定が存在する理由そのものを裏切る。

| 状況 | 扱い | なぜ |
|---|---|---|
| 値が無い | その項目だけ既定値 | 設定アプリが古い / 手で一部だけ作った |
| 型が違う | その項目だけ既定値 | 書き手とこのビルドの認識が食い違っている。推測はしない |
| 範囲外 | **最近傍にクランプ** | 9999 と書いた人は「できる限り良く」の意。100 はそれを叶える。10 に戻すと「無視された」ように見える |
| `Backend` が未知の名前 | 既定値。他は保持 | 新しい設定アプリであって、壊れた値ではない |
| `SchemaVersion` が未来 | **読めるものを読む** | 何が変わったか分からない以上、拒否するとユーザーは全設定を無視される |

`ZenzaiInferenceLimit` は**それまで無検証で Zenzai に渡っていた**。手編集で巨大な値を
入れると1打鍵のレイテンシが青天井になる。この決定で塞いだ。

DWORD は符号なしだが、**符号付き 32bit として読む**。設定アプリが `-1` を書けば
`0xFFFFFFFF` が格納され、それを 40億として読むと範囲チェックを素通りしてしまう。

## Windows 依存を Core に持ち込まない

`OhageyEngineCore` は移植可能でテスト可能であることが役割(決定 0029 と同じ趣旨)。
レジストリを読むには Windows が要るが、**値の意味を決めるのに Windows は要らない**。
そしてユーザーが気付く挙動は後者にある。

| | 置き場所 | 内容 |
|---|---|---|
| スキーマ | `OhageyEngineCore/SettingsSchema.swift` | 値名・範囲・既定値・`EngineSettings(values:)` |
| I/O | `OhageyEngine/RegistrySettings.swift` | `RegOpenKeyExW` / `RegEnumValueW` |
| 監視 | `OhageyEngine/SettingsWatcher.swift` | `RegNotifyChangeKeyValue` |

値は**名前で個別に問い合わせず、列挙して丸ごと Core に渡す**。このビルドが知らない
値を設定アプリが書いてもコストはゼロで、設定を1つ増やすときに I/O 側の変更が要らない。

## キーが無いときは作る

エンジンは起動時にキーを **`RegCreateKeyEx` で開く**(あれば開く、無ければ作る)。

読むためではなく、**監視するため**。`RegNotifyChangeKeyValue` は開いたキーを要求し、
存在しないキーは監視できない。新規プロファイルでは、ユーザーが設定アプリで何かを
変えても**エンジンが永久に気付かない**ことになり、ユーザーは「壊れている」と結論して
正しい。

空のキーを HKCU に作るのは「設定を書く」ことではない。エンジンは値を1つも入れない
(実機で確認済み)。

## 検証

| 確認したこと | 結果 |
|---|---|
| 起動時にキーを読む | `learning=false, backend=vulkan` を反映 |
| ホットリロード | `LearningEnabled` の変更を検知して `settings reloaded (learning=true)` |
| 再起動が要る項目の通知 | `Backend` 変更で `a restart is needed for: backend` |
| **新規プロファイル** | キー無し → 既定値、**空のキーだけ作成**(値ゼロ)、設定アプリの初回書き込みを即検知 |

`swift test` **112件パス**。

## 残る穴

- **エンジンを起動したのが別ユーザーのプロセスだった場合**、HKCU はそのユーザーのものを
  指す。パイプはセッション単位(決定 0006)なので通常は同一ユーザーだが、同一セッション内で
  昇格したプロセスが最初に接続した場合の挙動は未検証。
- グループポリシー(HKLM)による強制は**実装していない**。将来入れるなら HKLM を
  オーバーレイとして読み、UI に「管理者により固定」を出す形になる。今の規模では過剰。
